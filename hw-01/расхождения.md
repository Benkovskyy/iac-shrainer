# Дневник расхождений

## 1. Выбор зоны доступности

По варианту 06 для второй подсети предусмотрена зона `ru-central1-a`.

Во время выполнения работы возникли проблемы с получением публичных IP-адресов для создаваемых виртуальных машин. Для продолжения работы зона второй подсети была изменена на `ru-central1-b`.

В итоговой конфигурации используются:

- зона A: `ru-central1-d`;
- зона B: `ru-central1-b`.

Это значение приходится учитывать отдельно от исходных параметров варианта.

## 2. Публичные IP-адреса

Публичные IP-адреса web-серверов назначаются облаком автоматически и заранее неизвестны.

При создании стенда доступность конкретного публичного IP не гарантируется. В процессе работы встречались адреса, соединение с которыми из локального окружения не устанавливалось, поэтому требовалось повторное создание ресурса и дополнительная проверка доступности.

Скрипт не умеет автоматически определять, доступен ли выданный публичный IP из внешней сети пользователя, и при необходимости повторно получать другой адрес.

## 3. Доступ к серверу приложения

Сервер приложения `shrainer-app` намеренно создаётся без публичного IP.

Поэтому проверить его напрямую с локального компьютера нельзя. Проверка выполняется с одного из web-серверов по внутреннему IP сервера приложения.

Эту особенность необходимо учитывать при диагностике стенда.

## 4. Проверка балансировщика

Network Load Balancer использует внешний listener на порту `80`, а запросы передаются web-серверам на порт `8018`.

Для target group используется HTTP health check на порту `8018` и пути `/`.

При диагностике необходимо отдельно проверять:

- состояние балансировщика;
- состояние target group;
- результаты health check;
- работу nginx на web-серверах.

## 5. Повторный запуск create.sh

Скрипт проверяет наличие основных ресурсов и не создаёт их повторно, если они уже существуют.

Однако такой подход требует вручную учитывать состояние уже существующего ресурса. Сам факт существования ресурса ещё не гарантирует, что его конфигурация полностью соответствует текущей версии скрипта.

Например, если параметры уже существующего балансировщика были изменены, простой повторный запуск `create.sh` может пропустить его вместо пересоздания с новой конфигурацией.

## 6. Метки и поиск ресурсов

Ресурсы, создаваемые скриптом напрямую, получают метки `owner=shrainer` и `env=dev`.

Скрипт `destroy.sh` ищет ресурсы по этим меткам, а не по заранее известным именам. Такой подход не зависит от соглашения об именовании и позволяет отделять ресурсы конкретного владельца и окружения.

Исключение составляют загрузочные диски, создаваемые вместе с виртуальными машинами через `--create-boot-disk`: они не получают заданные скриптом метки. Эти диски удаляются автоматически вместе с ВМ благодаря параметру `auto_delete`.

Дополнительные диски web-серверов создаются отдельно, поэтому получают метки и могут быть найдены `destroy.sh` по ним.
